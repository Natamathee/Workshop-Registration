# โครงงานที่ 3: ระบบลงทะเบียนเข้าร่วมกิจกรรมอบรม (Project 3: Workshop Registration System)

## รายละเอียด (Description)

พัฒนาส่วนติดต่อผู้ใช้ (frontend) ให้แก่ **ระบบลงทะเบียนเข้าร่วมกิจกรรมอบรม (Workshop Registration System)** สำหรับให้ผู้ใช้งานค้นหาและลงทะเบียนเข้าร่วมกิจกรรมอบรมหรือ Workshop ต่าง ๆ โดยระบบส่วนหลัง (backend) ในโครงงานนี้ให้บริการ RESTful API สำหรับการทำงานดังกล่าว

## ความสามารถของระบบ (Features)

### การจัดการผู้ใช้ (User Management)

- รองรับบทบาทผู้ใช้ (roles) 2 แบบ ได้แก่ ผู้ดูแลระบบ (admin) และสมาชิก (member) โดยใช้ค่า `admin` และ `member`
- ผู้ใช้สามารถลงทะเบียน (register) โดยระบุชื่อ (`name`), อีเมล (`email`), หมายเลขโทรศัพท์ (`tel`), บทบาท (`role`) และรหัสผ่าน (`password`)
- หลังลงทะเบียน ผู้ใช้สามารถเข้าสู่ระบบ (login) ด้วยอีเมล (email) และรหัสผ่าน (password)
- ระบบออกโทเคน JWT (JWT token) หลังเข้าสู่ระบบ (login) เพื่อใช้เป็นข้อมูลยืนยันตัวตนของผู้ใช้ (user credential) และรองรับการออกจากระบบ (logout)
- Backend API มีการควบคุมสิทธิ์ (access control) และเส้นทางที่ต้องยืนยันตัวตน (protected routes)

### การจัดการกิจกรรมอบรม (Workshop Management)

- ผู้ใช้ทุกคนสามารถดู (view) ข้อมูลกิจกรรมอบรม (Workshop) ได้
- ผู้ใช้สามารถค้นหา (search) กิจกรรมจากชื่อ คำอธิบาย ผู้สอน หรือสถานที่ผ่าน `GET /api/v1/workshops?search=...`
- หลังเข้าสู่ระบบ `admin` สามารถเพิ่ม (add) แก้ไข (update) ลบ (delete) และดู (view) ข้อมูล Workshop
- กิจกรรมอบรม (Workshop) ที่สร้างใหม่ได้รับรหัสกิจกรรม (workshop id) สำหรับอ้างอิงในการแก้ไข (update) ลบ (delete) และลงทะเบียน (registration) โดย API ส่งรหัสกลับในฟิลด์ `_id`
- ข้อมูลประกอบด้วยชื่อกิจกรรม (name) คำอธิบาย (description) ผู้สอน (instructor) วันที่จัดกิจกรรม (workshop date) สถานที่ (location) และจำนวนที่รับได้ (capacity)

### การจัดการการลงทะเบียนเข้าร่วมกิจกรรม (Workshop Registration Management)

- หลังเข้าสู่ระบบ `member` สามารถสร้างการลงทะเบียน (registration) สำหรับ Workshop ใดก็ได้ที่เปิดใช้งานและผ่านเงื่อนไข โดยระบุรหัสกิจกรรม (workshop id)
- การลงทะเบียน (Registration) ที่สร้างใหม่ได้รับรหัสการลงทะเบียน (registration id) สำหรับใช้อ้างอิง โดย API ส่งรหัสกลับในฟิลด์ `_id`
- `member` สามารถดู (view) แก้ไข (edit) และลบ (delete) การลงทะเบียนของตนเอง
- `admin` สามารถดู (view) แก้ไข (edit) และลบ (delete) การลงทะเบียนของผู้ใช้ใดก็ได้

## เงื่อนไข (Conditions)

- วันที่จัดกิจกรรม (workshop date) ต้องไม่ก่อนวันปัจจุบัน
- จำนวนการลงทะเบียน (registration count) ต้องไม่เกินจำนวนที่รับได้ (capacity) ของกิจกรรมอบรม (Workshop)
- สมาชิก (member) สามารถลงทะเบียนกิจกรรมอบรม (Workshop) เดียวกันได้เพียง **1 การลงทะเบียน (registration)**
- สมาชิก (member) สามารถมีการลงทะเบียนที่ยังมีผล (active registrations) ได้รวมสูงสุด **3 กิจกรรมอบรม (Workshops)**
- ไม่สามารถลงทะเบียนกิจกรรมอบรม (Workshop) หลังวันที่จัดกิจกรรม (workshop date) ได้

## API ที่มีให้ใช้งาน (Available APIs)

โค้ดมี **API สำหรับการทำงานของระบบ 14 endpoints** และ **endpoints สำหรับตรวจสอบระบบและเอกสาร 3 endpoints**

Base URL เริ่มต้นคือ `http://localhost:5000` (เปลี่ยน `5000` เป็นค่าที่กำหนดใน `PORT`)

### API สำหรับยืนยันตัวตน (Authentication APIs)

| วิธี HTTP (HTTP Method) | เส้นทาง (Endpoint) | สิทธิ์การเข้าถึง (Access) | หน้าที่ / ข้อมูลในคำขอ (Purpose / JSON Request Body) |
|---|---|---|---|
| POST | `/api/v1/auth/register` | ทุกคน (Public) | ลงทะเบียนด้วย `name`, `email`, `tel` และ `password` โดยบัญชีใหม่เป็น `member` เสมอ ส่งกลับข้อมูลผู้ใช้และ JWT; บัญชี `admin` ต้องจัดเตรียมแยกโดยผู้ดูแลระบบ |
| POST | `/api/v1/auth/login` | ทุกคน (Public) | เข้าสู่ระบบด้วย `email` และ `password` ส่งกลับข้อมูลผู้ใช้และ JWT |
| GET | `/api/v1/auth/me` | `member` หรือ `admin` | ดูข้อมูลผู้ใช้ที่ยืนยันตัวตนอยู่ในขณะนั้น |
| GET | `/api/v1/auth/logout` | `member` หรือ `admin` | ล้าง cookie ที่เก็บ token |

Protected APIs รับข้อมูลยืนยันตัวตนจาก header `Authorization: Bearer <token>` เท่านั้น การลงทะเบียนและเข้าสู่ระบบตั้งค่า cookie ชื่อ `token` ด้วย แต่ middleware ไม่อ่าน cookie นี้ การออกจากระบบล้าง cookie โดยไม่ได้เพิกถอน bearer token ที่ออกไปแล้ว

### API สำหรับกิจกรรมอบรม (Workshop APIs)

| วิธี HTTP (HTTP Method) | เส้นทาง (Endpoint) | สิทธิ์การเข้าถึง (Access) | หน้าที่ / ข้อมูลในคำขอ (Purpose / JSON Request Body) |
|---|---|---|---|
| GET | `/api/v1/workshops` | ทุกคน (Public) | ดูรายการ Workshop ที่เปิดใช้งาน เรียงตามวันที่จัดกิจกรรมและชื่อ รองรับ `?search=` |
| GET | `/api/v1/workshops/:id` | ทุกคน (Public) | ดูรายละเอียด Workshop ที่เปิดใช้งานหนึ่งรายการ |
| POST | `/api/v1/workshops` | `admin` | สร้าง Workshop ด้วย `name`, `description`, `instructor`, `workshopDate`, `location` และ `capacity` |
| PUT | `/api/v1/workshops/:id` | `admin` | แก้ไข Workshop ที่เปิดใช้งานตามฟิลด์ที่ส่งมา โดยตรวจสอบวันที่ จำนวนที่รับได้ และผลต่อการลงทะเบียนเดิม |
| DELETE | `/api/v1/workshops/:id` | `admin` | ลบแบบ soft delete โดยตั้งค่า `isActive: false` และเก็บประวัติการลงทะเบียนไว้ |

ตัวอย่างคำขอสร้างกิจกรรม (Workshop Request Example):

```json
{
  "name": "Introduction to Photography",
  "description": "Learn practical camera skills",
  "instructor": "Example Instructor",
  "workshopDate": "2026-12-01",
  "location": "Training room A",
  "capacity": 20
}
```

เปลี่ยนวันที่ในตัวอย่างให้เป็นวันปัจจุบันหรืออนาคตเมื่อลองใช้งานจริง ชื่อกิจกรรมสามารถซ้ำได้ เช่น หลักสูตรเดียวกันที่จัดต่างวัน `capacity` ต้องเป็นจำนวนเต็มตั้งแต่ `1` ขึ้นไป การแก้ไขต้องไม่ลด `capacity` ต่ำกว่าจำนวนการลงทะเบียนที่มีอยู่

การค้นหา (Search) ใช้ข้อความบางส่วนโดยไม่แยกตัวพิมพ์ใหญ่เล็กใน `name`, `description`, `instructor` หรือ `location` โดยถืออักขระพิเศษเป็นข้อความธรรมดา รายการรวม Workshop ที่ผ่านวันจัดแล้วหากยังไม่ถูกลบ ปัจจุบันไม่มีตัวกรองอื่นหรือการแบ่งหน้า (pagination)

### API สำหรับการลงทะเบียน (Registration APIs)

| วิธี HTTP (HTTP Method) | เส้นทาง (Endpoint) | สิทธิ์การเข้าถึง (Access) | หน้าที่ / ข้อมูลในคำขอ (Purpose / JSON Request Body) |
|---|---|---|---|
| GET | `/api/v1/registrations` | `member` หรือ `admin` | `member` ได้รับเฉพาะการลงทะเบียนของตนเอง ส่วน `admin` ได้รับทั้งหมด รวมประวัติ เรียงตามวันที่สร้าง |
| GET | `/api/v1/registrations/:id` | เจ้าของการลงทะเบียน หรือ `admin` | ดูการลงทะเบียนพร้อมรายละเอียดผู้ใช้และ Workshop ที่เกี่ยวข้อง |
| POST | `/api/v1/registrations` | เฉพาะ `member` | สร้างการลงทะเบียนด้วย `workshop` ซึ่งเป็น MongoDB ID ของกิจกรรม |
| PUT | `/api/v1/registrations/:id` | เจ้าของการลงทะเบียน หรือ `admin` | เปลี่ยน Workshop ที่เข้าร่วมด้วย `workshop` โดยคงเจ้าของและ ID การลงทะเบียนเดิม |
| DELETE | `/api/v1/registrations/:id` | เจ้าของการลงทะเบียน หรือ `admin` | ลบการลงทะเบียนออกจากฐานข้อมูลอย่างถาวร และคืนที่ว่างให้กิจกรรม |

ตัวอย่างคำขอลงทะเบียน (Registration Request Example):

```json
{
  "workshop": "<workshop MongoDB ID>"
}
```

เงื่อนไขและการตีความที่ใช้ในโค้ด (Implemented Rules and Interpretations):

- `workshopDate` ต้องเป็นวันที่มีอยู่จริงในรูปแบบ `YYYY-MM-DD` โดยใช้ **UTC** ในการกำหนดวันปัจจุบัน เช่นเดียวกับ PJ01/PJ02
- ลงทะเบียนได้ถึงวันจัดกิจกรรม รวมถึงวันปัจจุบัน เพราะข้อกำหนดระบุเพียงวันที่ ไม่ได้ระบุเวลาเริ่มกิจกรรม
- การลงทะเบียนที่ยังมีผล (active registration) หมายถึงการลงทะเบียนที่ยังไม่ถูกลบและอ้างอิง Workshop ที่ `isActive=true` และ `workshopDate` เป็นวันนี้หรืออนาคต ไม่มีฟิลด์สถานะ active แยกใน registration
- การลงทะเบียนของ Workshop ที่ผ่านวันจัดหรือถูก soft delete ไม่ถูกนับในเพดาน 3 Workshops แต่ยังดูและลบประวัติได้
- ตรวจสอบการลงทะเบียนซ้ำ ความจุ และเพดาน 3 Workshops ทั้งการสร้างและแก้ไข โดยไม่นับรายการที่กำลังแก้ไขซ้ำอีกครั้ง
- การแก้ไขการลงทะเบียน (Edit registration) คือการย้ายไป Workshop อื่นที่ผ่านเงื่อนไข หากไม่ส่ง `workshop` จะคงกิจกรรมเดิมและตรวจสอบเงื่อนไขอีกครั้ง ค่า `null` ไม่ถือว่าเป็นการละเว้นฟิลด์
- เจ้าของการลงทะเบียนมาจากผู้ใช้ที่ยืนยันตัวตน ไม่รับค่า `user` จาก request body และไม่อนุญาตให้แก้ไขเจ้าของ `admin` สร้าง registration ไม่ได้ แต่จัดการของสมาชิกได้
- การเลื่อนวันจัด Workshop เดิมต้องไม่ทำให้สมาชิกที่ลงทะเบียนไว้มี active registrations เกิน 3 รายการ
- มี unique index บน `(user, workshop)` เพื่อป้องกันการลงทะเบียนซ้ำในฐานข้อมูล และจัดลำดับการเปลี่ยนแปลง Workshop/registration ผ่าน [middleware/serialize.js](middleware/serialize.js) เพื่อให้การตรวจนับและเขียนข้อมูลไม่แทรกกันภายใน Node.js process เดียว
- การตรวจความจุและเพดาน active registrations ใช้การนับก่อนเขียนข้อมูล โดยรองรับการทำงานผ่าน backend process เดียว หากใช้หลาย process หรือหลาย server instances ต้องเพิ่มการประสานงานระดับฐานข้อมูล เช่น transaction/locking
- ไม่มีขั้นตอนอนุมัติ รายชื่อรอ (waitlist) เช็กชื่อเข้าร่วม หรือชำระเงินในข้อกำหนดปัจจุบัน

### เส้นทางสำหรับตรวจสอบระบบและเอกสาร (System and Documentation Endpoints)

| วิธี HTTP (HTTP Method) | เส้นทาง (Endpoint) | สิทธิ์การเข้าถึง (Access) | หน้าที่ (Purpose) |
|---|---|---|---|
| GET | `/` | ทุกคน (Public) | แสดงข้อความต้อนรับและลิงก์เอกสารกับการตรวจสอบสถานะ |
| GET | `/health` | ทุกคน (Public) | แสดงสถานะ application, timestamp และ environment โดยไม่ตรวจสอบการเชื่อมต่อฐานข้อมูล |
| GET | `/api-docs` | ทุกคน (Public) | แสดง Swagger UI สำหรับ API ของระบบและ utility endpoints |

### รูปแบบการตอบกลับ (Response Format)

การสร้างข้อมูลสำเร็จส่งกลับ `201` ส่วนการทำงานอื่นของ application ที่สำเร็จส่งกลับ `200` โดยทั่วไป response ใช้ `{ success, data }` และเพิ่ม `count` สำหรับรายการ ส่วน JWT ส่งกลับใน `data.token`

ข้อผิดพลาดใช้ `{ success: false, error }` การผิดรูปแบบข้อมูลหรือวันจัดกิจกรรมส่งกลับ `400` การไม่ยืนยันตัวตนส่งกลับ `401` การไม่มีสิทธิ์ส่งกลับ `403` และการไม่พบข้อมูลส่งกลับ `404` ส่วนการลงทะเบียนซ้ำ กิจกรรมเต็ม เพดาน 3 Workshops หรือการเปลี่ยน Workshop ที่ขัดกับการลงทะเบียนเดิมส่งกลับ `409`

ข้อผิดพลาดจากฐานข้อมูลที่ไม่ได้จัดการเฉพาะ เช่น Mongoose validation/cast error ส่งต่อไป global error handler และใช้ `500` เป็นค่าเริ่มต้นตามรูปแบบ PJ01/PJ02 ยกเว้น duplicate-key error ของ registration ซึ่งจัดการเป็น `409`

## กลไกการยืนยันตัวตน (Authentication)

Authentication controller อยู่ใน [controllers/auth.js](controllers/auth.js) ส่วน methods สำหรับ password และ JWT อยู่ใน [models/User.js](models/User.js) ใช้รูปแบบเดียวกับ PJ01/PJ02

### การลงทะเบียน เข้าสู่ระบบ และสร้างโทเคน (Registration, Login, and Token Generation)

1. `POST /api/v1/auth/register` สร้างผู้ใช้ โดย user model hash password ด้วย bcrypt ก่อนบันทึก และส่งกลับ HTTP `201`
2. `POST /api/v1/auth/login` ตรวจสอบ email และเปรียบเทียบ password กับ bcrypt hash แล้วส่งกลับ HTTP `200`
3. ทั้งสอง endpoint เรียก `sendTokenResponse()` สร้าง JWT ซึ่งมี ID ของผู้ใช้ ลงลายเซ็นด้วย `JWT_SECRET` และกำหนดอายุผ่าน `JWT_EXPIRE`
4. JWT เดียวกันส่งกลับใน `data.token` และ cookie ชื่อ `token`

ตัวอย่างการตอบกลับเมื่อยืนยันตัวตนสำเร็จ (Successful Authentication Response):

```json
{
  "success": true,
  "data": {
    "id": "507f1f77bcf86cd799439011",
    "name": "Example Member",
    "email": "member@example.com",
    "role": "member",
    "token": "<JWT>"
  }
}
```

### การยืนยันตัวตนด้วยโทเคน Bearer (Bearer Token Authentication)

Client แนบ token กับทุก request ที่ต้องยืนยันตัวตน:

```http
GET /api/v1/registrations HTTP/1.1
Authorization: Bearer <JWT>
```

Middleware `protect` ใน [middleware/auth.js](middleware/auth.js) อ่าน bearer header ตรวจสอบลายเซ็นและอายุ JWT แล้วค้นหาผู้ใช้ตาม ID หากไม่มี token, token ใช้ไม่ได้ หรือไม่มีผู้ใช้นั้น จะส่งกลับ `401` เมื่อผ่านการตรวจสอบจะเก็บผู้ใช้ใน `req.user`

Middleware `authorize` ตรวจสอบ role ส่วน controller ตรวจสอบความเป็นเจ้าของการลงทะเบียน หากไม่มีสิทธิ์จะส่งกลับ `403`

### คุกกี้และโทเคน Bearer (Cookie and Bearer Token)

| ตัวเลือกคุกกี้ (Cookie Option) | การทำงาน (Behavior) |
|---|---|
| `httpOnly` | JavaScript ใน browser อ่าน cookie ผ่าน `document.cookie` ไม่ได้ |
| `expires` | คำนวณจาก `JWT_COOKIE_EXPIRE` ซึ่งมีหน่วยเป็นวัน |
| `secure` | เปิดใช้เมื่อ `NODE_ENV` เป็น `production` |

`JWT_EXPIRE` กำหนดอายุ JWT ส่วน `JWT_COOKIE_EXPIRE` กำหนดอายุ cookie ซึ่งเป็นค่าที่แยกกัน การส่งเฉพาะ cookie ไม่สามารถยืนยันตัวตนได้ เพราะ `protect` ไม่อ่าน `req.cookies.token` หาก bearer JWT หมดอายุหรือไม่ถูกต้อง จะส่งกลับ `401` แม้ cookie จะมีค่าที่ถูกต้อง

### การใช้การยืนยันตัวตนใน Swagger (Swagger Authorization)

ที่ `/api-docs` ให้คัดลอก `data.token` หลังลงทะเบียนหรือเข้าสู่ระบบ คลิก **Authorize** แล้ววาง JWT โดยไม่เติม `Bearer ` เพราะ Swagger เติมให้ใน header ไม่มีตัวเลือก `cookieAuth`

### การออกจากระบบและการหมดอายุของโทเคน (Logout and Token Expiration)

`GET /api/v1/auth/logout` ต้องใช้ bearer token ที่ถูกต้อง โดย controller แทนค่า cookie ด้วย `none` และกำหนดให้หมดอายุในอีก 10 วินาที การออกจากระบบไม่เพิกถอน JWT ดังนั้น frontend ต้องลบ bearer token ที่เก็บไว้ และผู้ใช้ Swagger ต้องล้าง authorization แยกต่างหาก Backend ไม่มี refresh-token endpoint เมื่อ token หมดอายุต้องเข้าสู่ระบบใหม่

## การตั้งค่าและตรวจสอบ (Setup and Verification)

ติดตั้ง dependencies ด้วย `npm ci` จาก directory `PJ03-WorkshopRegist` โดย dependency ranges และ locked versions ตรงกับ PJ02-EquipmentRent ใช้ Node.js, Express 5, Mongoose 8, JWT, bcryptjs, Swagger, Helmet, CORS, HPP และ rate limiting ในรูปแบบเดียวกัน

`MONGO_URI` ใน [config/config.env](config/config.env) **เว้นว่างไว้ตามที่กำหนด** เมื่อต้องการใช้ API ที่เข้าถึงฐานข้อมูลให้ตั้งค่า MongoDB connection string และใช้ `npm run dev` หรือ `npm start` กำหนด `JWT_SECRET` ของตนเองก่อน deploy ค่าในไฟล์ถูกสร้างสำหรับการพัฒนาภายในเครื่อง

เมื่อ `MONGO_URI` ว่าง server ยังเปิด welcome endpoint, health endpoint และ Swagger UI ได้ หากรันโครงงานอื่นพร้อมกันให้ตั้ง `PORT` ของแต่ละโครงงานต่างกัน ค่าเริ่มต้นคือ `5000` และ frontend สำหรับการพัฒนาคือ `http://localhost:3000`

`npm test` ตรวจ syntax ของ entry point ตาม PJ01/PJ02 การตรวจสอบระหว่างพัฒนาใช้ API จริงกับ model persistence ในหน่วยความจำ โดยไม่เชื่อมต่อฐานข้อมูล จึงยังต้องตรวจสอบกับ MongoDB จริงผ่าน Swagger หลังตั้งค่า `MONGO_URI` แล้ว ระบบจำกัด 100 requests ต่อ IP ใน 10 นาที
